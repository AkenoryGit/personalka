# Сервер на VPS: установка и выкладка

Сервер «Персоналки» стоит на VPS Planovo (`195.24.71.37`, Рег.облако, Москва, Ubuntu 24.04), но полностью отдельно (ТЗ 7.4): своя служба `trener.service`, свой пользователь `trener`, своя база `trener` в том же PostgreSQL 16, свой поддомен `trener.planovo-app.ru` в том же Caddy. Planovo при этом не трогается — ни его служба, ни база, ни брандмауэр, ни его блок в Caddyfile.

Руками на сервере ничего не ставится: всё делает выкладка из GitHub Actions — по образцу Planovo (`AkenoryGit/planovo`, `deploy/setup.sh` и `.github/workflows/server.yml`). Вход — `root` по ключу выкладки, как у Planovo.

| Файл | Куда на VPS | Что |
| --- | --- | --- |
| [`setup.sh`](setup.sh) | запускается из `/root/personalka-deploy` | Установка и обновление: пакеты (если Planovo их ещё не поставил), пользователь, папки, роль и база, `/etc/trener/trener.env`, службы, блок Caddy. Повторный запуск ничего не ломает |
| [`server.sh`](server.sh) | `/opt/trener/bin/` | Переключение версии, проверка `/health`, откат |
| [`trener.service`](trener.service) | `/etc/systemd/system/` | Служба: пользователь `trener`, Java 21 до 384 МБ, перезапуск через 5 с, урезанные права |
| [`backup.sh`](backup.sh), [`backup_mail.py`](backup_mail.py), [`backup.pub`](backup.pub) | `/opt/trener/bin/` | Ночная копия базы (ТЗ 7.5): дамп, шифрование age, письмо, чистка ящика, проба восстановления — раздел «Копии базы» ниже |
| [`trener-backup.service`](trener-backup.service), [`trener-backup.timer`](trener-backup.timer) | `/etc/systemd/system/` | Запуск копии каждый день в 03:30 по Тюмени; пропущенный — сразу после включения сервера |
| [`trener-alert.service`](trener-alert.service) | `/etc/systemd/system/` | Письмо, когда служба упала 5 раз за 10 минут: через `planovo-alert` — ящик Planovo и его `ALERT_EMAIL` |

**Что где на сервере:** версии — `/opt/trener/releases/<N>/personalka-server.jar`, включённая — ссылка `/opt/trener/current`; Java 21 — ссылка `/opt/trener/java`; настройки — `/etc/trener/trener.env` (root, группа `trener`, 640); пароль базы — `/etc/trener/db-password` (только root; создаётся на сервере, нигде больше не хранится); блок Caddy — `/etc/caddy/sites/trener.caddy`.

**Caddy — общий с Planovo.** Выкладка Planovo пишет `/etc/caddy/Caddyfile` целиком заново, поэтому блок «Персоналки» лежит своим файлом, а в Caddyfile — одна строка `import /etc/caddy/sites/*.caddy`. `setup.sh` дописывает её сам, если её нет; `setup.sh` Planovo пишет её в конце своего Caddyfile (иначе каждая выкладка Planovo выключала бы поддомен «Персоналки» до следующей выкладки «Персоналки»). Нет файлов в `sites/` — Caddy только предупреждает в журнале.

**Порты:** Planovo — `127.0.0.1:8080`, «Персоналка» — `127.0.0.1:8090`; снаружи открыты только 22, 80, 443 (брандмауэр настраивает Planovo).

## Как идёт выкладка

1. **«Сборка»** (`build.yml`) на `main`: тесты всех модулей, в том числе сервера на PostgreSQL 16, и `personalka-server.jar` в релизе «Последняя сборка» рядом с APK.
2. **«Выкладка сервера»** (`deploy.yml`) запускается сама после зелёной «Сборки» в `main` и вручную (Actions → «Выкладка сервера» → Run workflow):
   - **«Проверка установки»** — тот же `setup.sh` на чистой Ubuntu 24.04 в CI рядом с поддельным сайтом Planovo: установка, включение версии, ответ через Caddy по поддомену, повторная установка, Caddyfile, переписанный «выкладкой Planovo», версия, которая не ответила, права на файлы настроек. Идёт и в ветках, где менялись `deploy/` или `deploy.yml` (jar — из `main`).
   - **«Выкладка»** — по SSH от `root` кладёт jar и папку `deploy/`, запускает `setup.sh`, потом `server.sh switch <N>`; в итогах сборки — строка «Сервер настроен» (система, Java, PostgreSQL, свободная память и диск), затем проверка `https://trener.planovo-app.ru/health` снаружи и что `https://planovo-app.ru/health` по-прежнему отвечает.
3. **`server.sh`** переводит ссылку `/opt/trener/current` на новую версию, перезапускает службу и ждёт до 60 секунд ответа `/health` с этим номером версии. Не дождался — возвращает прежнюю версию сам и помечает новую как упавшую; выкладка в Actions краснеет. Хранятся 5 последних версий.
4. **«Откат сервера»** (`rollback.yml`) — ручная кнопка: Actions → «Откат сервера» → Run workflow. Включает ближайшую младшую версию, которая не падала. Схема базы назад не откатывается.

Пока нет секретов, выкладка пропускается — сборка и APK от этого не зависят.

`/health` отвечает 200 и тремя строками — `ok`, `версия 0.1.N`, `схема M`; если база не отвечает — 503 «база не отвечает». Данных тренеров в ответе нет.

## Секреты GitHub (Settings → Secrets and variables → Actions)

| Секрет | Что это |
| --- | --- |
| `PERSONALKA_SERVER` | IP-адрес VPS |
| `PERSONALKA_SSH_KEY` | Закрытый ключ выкладки `personalka_deploy` (ed25519); открытая часть — в `/root/.ssh/authorized_keys` на сервере |
| `MAIL_PASSWORD` | Пароль приложения Mail.ru для ящика Planovo (SMTP и IMAP) — для писем с кодами (2.8) и копий (2.14). Нет его — берётся пароль Planovo из `/etc/planovo/ops.env` |
| `MAIL_USER` | Необязательно: свой ящик «Персоналки»; нет — адрес ящика Planovo из `/etc/planovo/ops.env` |
| `PERSONALKA_ADMIN_EMAIL` | Необязательно: почта администратора; нет — `ALERT_EMAIL` Planovo (почта для писем о сбоях) |

**Письма с кодами** (регистрация и сброс пароля, шаг 2.8) идут через ящик Planovo: `setup.sh` берёт `MAIL_USER`, `MAIL_PASSWORD`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_TLS`, `ALERT_EMAIL` из `/etc/planovo/ops.env` (его пишет выкладка Planovo), секреты «Персоналки» главнее. Выкладка передаёт их файлом, который удаляется сразу после установки; в `/etc/trener/trener.env` они попадают как `TRENER_SMTP_*`, `TRENER_MAIL_FROM` («Персоналка <адрес ящика>») и `TRENER_ADMIN_EMAIL`. В итогах выкладки, в строке «Сервер настроен», — какой ящик и кто администратор (адреса скрыты звёздочками).

Ключ сервера запоминается при первом входе (`StrictHostKeyChecking=accept-new`), как у Planovo.

## Копии базы (ТЗ 7.5)

**Каждую ночь в 03:30 по Тюмени** `backup.sh` (служба `trener-backup`, от root):

1. `pg_dump` базы `trener` и проверка, что дамп читается (`pg_restore --list`); число записей по таблицам — из дампа.
2. **По воскресеньям — проба восстановления:** дамп разворачивается во временную базу `trener_probe`, число записей в каждой таблице сверяется с дампом, база удаляется. Закрытого ключа на сервере нет, поэтому проба берёт дамп до шифрования — те же байты, что потом шифруются (их SHA-256 — в письме).
3. **Шифрование** `age` открытым ключом [`backup.pub`](backup.pub). Закрытый ключ `personalka-backup.key` — только у Дмитрия, в двух местах.
4. **Письмо** в ящик Planovo (туда же, куда копии Planovo) с темой «Персоналка: копия базы 25.10.2026 [personalka-backup]». Копия больше 15 МБ уходит несколькими письмами «· часть 1 из 2». На сервере — 7 последних зашифрованных копий в `/var/backups/trener` (только root).
5. **Чистка ящика по IMAP** (`imap.mail.ru`, тот же пароль приложения): во всех папках удаляются письма с меткой `[personalka-backup]` в теме старше 30 дней — остаются сегодняшняя и 29 прошлых. Письма Planovo и любые другие не трогаются.
6. **Сбой на любом этапе** — письмо администратору («Персоналка: копия базы не сделана», этап и код), не вышло своим ящиком — через `planovo-alert`. Итог последнего запуска — строкой в `/var/lib/trener/backup-status` (время, `ok` или `ошибка`, подробности); её покажет «Клуб → Сервер», когда появится этот экран (этап 5). Итог виден и в строке «Сервер настроен» каждой выкладки.

Первую копию с пробой выкладка делает сама сразу после установки (если отметки ещё нет) — в итогах сборки «Первая копия базы». Вручную на сервере: `systemctl start trener-backup` (проба — `/opt/trener/bin/backup.sh --probe`), журнал — `journalctl -u trener-backup -n 100`.

**Как восстановить** (нужен закрытый ключ; `age` — [age-encryption.org](https://age-encryption.org), на Windows — `age.exe` из релиза):

```
# частей несколько — склеить по порядку
cat trener-20261025-0330.dump.age.01 trener-20261025-0330.dump.age.02 > trener-20261025-0330.dump.age
age --decrypt --identity personalka-backup.key trener-20261025-0330.dump.age > trener.dump
pg_restore --list trener.dump          # проверка: дамп читается
sha256sum trener.dump                  # совпадает с SHA-256 в письме
# на сервере: служба остановлена, база пустая (createdb -O trener trener)
sudo -u postgres pg_restore --no-owner --role=trener --dbname=trener < trener.dump
```

Проверить ключ, не трогая сервер, — первые две строки и `pg_restore --list` на своём компьютере.

## Открыть возможность тренеру (ТЗ 1.5)

Пока нет экрана «Тренеры» (этап 5), возможность открывает администратор строкой в базе. Тренер сначала регистрируется в приложении («Настройки → Данные → Аккаунт»). На сервере по SSH — например, «Официально с налогом 6,5 %» до конца года:

```sh
sudo -u postgres psql trener -c "INSERT INTO coach_feature (coach_id, feature, until)
  SELECT id, 'half_official', DATE '2026-12-31' FROM coach WHERE email = 'почта тренера'
  ON CONFLICT (coach_id, feature) DO UPDATE SET until = EXCLUDED.until"
```

`until` — последний день включительно, `NULL` — без срока. Коды: `half_official` («Официально с налогом 6,5 %»), `cabinets` («Кабинеты родителей», открывают и копию), `server_copy` («Копия на сервере»). Закрыть — `DELETE FROM coach_feature WHERE feature = '…' AND coach_id = (SELECT id FROM coach WHERE email = '…')`. Телефон тренера увидит изменение, когда тренер откроет «Аккаунт» (экран спрашивает сервер). У администратора (`TRENER_ADMIN_EMAIL`) открыто всё и без строк.

## Если что-то не так

- **Выкладка красная** — в итогах сборки последние 25 строк с сервера: что не поставилось или какая версия не ответила.
- **`https://trener.planovo-app.ru` не отвечает, а выкладка зелёная** — запись A `trener` → IP сервера в DNS (Beget); сертификат Caddy получит сам, как только запись дойдёт.
- **Поддомен пропал после выкладки Planovo** — в `setup.sh` Planovo нет строки `import /etc/caddy/sites/*.caddy`; пока её нет, вернёт поддомен любая выкладка «Персоналки» (Actions → «Выкладка сервера» → Run workflow).
- **Сервер пропал** — новый VPS → секрет `PERSONALKA_SERVER` → выкладка поставит всё заново. Данные — из копии (шаг резервного копирования) и из телефона тренера: полная копия всегда там.
