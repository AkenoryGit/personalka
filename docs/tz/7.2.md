# 7.2. Протокол синхронизации

Раздел [7. Сервер и синхронизация](7.md) · [оглавление ТЗ](README.md)

1. **Локальное изменение** записывается в базу и ставит запись в Outbox (повторные изменения одной записи склеиваются) — в одной транзакции.
2. **Push:** пачки до 500 изменений `{entity, id, version, updated_at, deleted_at, data}`. Сервер принимает строку, если её `updated_at` новее хранящегося (при равенстве — по идентификатору устройства), и присваивает ей сквозной номер `seq`; старые строки пропускает. `updated_at` из будущего больше чем на 5 минут заменяется временем сервера. Принятые записи удаляются из Outbox.
3. **Pull:** все изменения тренера и клуба с `seq` больше последнего полученного, постранично. Устройство применяет строку, если она новее локальной (то же правило «последнее изменение побеждает»).
4. **Когда:** сначала push, потом pull — при запуске, при возврате в приложение, через 5 секунд после последнего изменения, раз в 15 минут в фоне при наличии сети, вручную. Ошибка сети — повтор с нарастающей паузой (до 15 минут).
5. **Первая выгрузка** при подключении сервера — все записи телефона с полосой прогресса. **Новое устройство** — полный pull с нуля.
6. **Удалённые записи** хранятся 90 дней. Устройство, не синхронизировавшееся дольше, получает ответ «нужна полная синхронизация»: сначала отправляет свои изменения, потом забирает всё заново.
7. **Версии схемы:** каждый запрос несёт `schema_version`; сервер поддерживает текущую и предыдущую. Слишком старое приложение получает 426 и просьбу обновиться; работа на телефоне при этом не блокируется.
8. **Ссылочная целостность:** сервер принимает записи в любом порядке (участие раньше тренировки), внешние ключи между синхронизируемыми таблицами не ставятся. Все запросы фильтруются по `coach_id` из сессии — чужие записи недоступны ни на чтение, ни на запись.

*Уточнено на шаге 2.9 (24.10.2026), сервер:*

- **Отправка:** `POST /sync/push` `{schema_version, device_id, changes: [{entity, id, version, updated_at, deleted_at, data}]}`; `updated_at` и `deleted_at` — миллисекунды UTC, `data` — строка таблицы телефона целиком (JSON), `entity` — имя таблицы телефона. В ответе `results` — по изменению на каждое: `accepted` (с `seq`), `stale` (у сервера новее — придёт при выдаче), `club_only` (данные клуба от не-администратора). Из Outbox убираются все три. **Повтор** той же отправки (тот же момент и то же устройство) отвечает `accepted` с прежним `seq` и ничего не меняет. Ошибка в любом изменении (неизвестная таблица, нет `updated_at`, больше 500, запись больше 64 КБ) — 400 на всю пачку, ничего не записывается.
- **Выдача:** `GET /sync/pull?since=&limit=&schema_version=` (по умолчанию 500, не больше 1000) → `changes` (с `device_id` и `seq`), `last_seq`, `has_more`. Удалённые после `since` уже стёрты — **410 `full_sync`**; выдача с `since=0` работает всегда.
- **Область:** запись клуба — у таблицы `club_rate_grid` и у записей с `scope = CLUB`; их получают все тренеры с открытой «Копией на сервере». Записи тренера хранятся отдельно по тренеру: тот же `id` у другого тренера — его отдельная запись.
- **Версия схемы** — номер версии базы телефона (`SyncRules.SCHEMA_VERSION`). Старше предыдущей или без номера — 426 `update_required`; новее сервера (сервер ещё не обновился) — 503 `server_outdated`, изменения остаются в Outbox.
- **Доступ:** синхронизация — только с открытой «Копией на сервере» (403 `feature_closed`; срок вышел — данные не стираются), приостановленному — 403 `suspended`.
- **Хранение:** сервер не разбирает строки таблиц: сравнивает только служебные поля, `data` хранит как есть (JSONB). Номера `seq` — сквозные на сервер, отправки идут по одной, поэтому выдача «после номера» ничего не пропускает. Удалённые больше 90 дней назад стираются при запуске сервера и раз в сутки.

*Уточнено на шаге 2.10 (24.10.2026), телефон:*

- **Очередь** — таблица `sync_outbox` (3.8), её пишут триггеры SQLite у каждой синхронизируемой таблицы на вставку, изменение и стирание: в очередь попадает любая правка, и ни одну не надо помнить в коде. «Удалить полностью» (3.1) уходит удалением с пустыми данными (`data: {}`) и моментом не раньше последней правки записи; другой телефон, получив такое, стирает запись у себя.
- **Отправка:** пачки по 500 из очереди, сначала давние; из очереди убираются ответы `accepted`, `stale`, `club_only`, но только если запись не менялась после чтения — новая правка уйдёт следующей пачкой. Ответ потерян — та же пачка уходит ещё раз, сервер дубля не пишет.
- **Получение:** страница выдачи применяется одной транзакцией, номер `since` запоминается после неё. Своя правка ещё в очереди — правило сервера («позже побеждает», при равенстве — большее устройство); уже отправлена — применяется всё, что не старше своей. Запись стёрта на телефоне и удаление ещё не ушло — пришедшая правка её не воскрешает. Пришедшее с сервера в очередь не попадает. 410 — получение с начала после отправки своего.
- **Подключение:** обычное — вся база в очередь и выгрузка с полосой прогресса, потом получение с начала. Новое устройство («Войти» на первом запуске, 5.18) — данные телефона заменяются данными с сервера; телефон стирается, только когда сервер ответил первой страницей, — без связи или без открытой копии ничего не теряется. Отказ сервера при подключении (копия закрыта, приостановлен, вход устарел) — сервер не подключается.
- **Ошибки:** нет связи, сбой сервера, 503 — повтор через 30 с, 1, 2, 4, 8, потом каждые 15 минут; 426, 403, 401 — обмен стоит до следующего раза (раз в 15 минут), очередь не трогается. Через 5 секунд после правки обмен идёт, только пока ошибок нет.
- **После восстановления из копии** (7.6) вся база ложится в очередь заново, получение — с начала: восстановленное сливается с сервером (новее — побеждает), стёртое при замене удалением на сервер не уходит.
- **Отключение** — `DELETE /account/data`; на телефоне всё остаётся, без связи сервер остаётся подключённым.

*Уточнено на шаге 2.10а (24.10.2026), экраны и фон:*

- **Когда (п. 4) на Android:** пока процесс приложения жив, обмен ведёт `SyncRunner` — при запуске, через 5 секунд после правки, раз в 15 минут, при каждом возврате в приложение и по кнопке «Синхронизировать». При закрытом приложении — задача JobScheduler раз в 15 минут с условием «есть сеть», переживает перезагрузку; стоит, только пока сервер подключён. WorkManager не нужен: на Android 10+ JobScheduler делает то же без лишней библиотеки.
- **Перед подключением** телефон спрашивает выдачу с начала: есть данные тренера (не клуба) — предлагается только «Взять данные с сервера» (5.16); нет — первая выгрузка.
